Montage GLPI sécurisé

Deux machines Ubuntu, un serveur GLPI joignable uniquement à travers un tunnel VPN, une double authentification et une sonde Suricata en mode blocage. Les étapes suivent les priorités du cahier de recettes, avec à chaque fois la preuve à capturer pour le rapport.

Serveursrv-glpiUbuntu Server 24.04 · 4 Go RAM · 2 vCPU · 25 Go
Clientpc-clientUbuntu Desktop 24.04 · 2 Go RAM · 1 vCPU · 20 Go
Tunnel10.8.0.0/24WireGuard, UDP 51820, seul port ouvert
Étape 01

Réseau et machines

Très hauteDeux VM sur un même réseau, le serveur ne sera joignable que par le VPN une fois l'étape 04 terminée.

Créez les deux machines dans votre hyperviseur (VirtualBox, VMware Workstation ou Proxmox) sur un même réseau. En VirtualBox, le plus simple est un adaptateur « Réseau NAT » commun ou un « Accès par pont » sur le réseau de la salle. Le client et le serveur doivent se pinguer avant d'aller plus loin.

MachineNom d'hôteIP LAN (exemple)IP VPNRôles
VM 1srv-glpi192.168.1.1010.8.0.1GLPI, MariaDB, WireGuard, UFW, Suricata, Postfix/Dovecot
VM 2pc-client192.168.1.2010.8.0.2Agent GLPI, pair WireGuard, serveur VNC

Adaptez les adresses LAN à ce que votre réseau attribue, mais gardez le plan VPN tel quel : toutes les commandes du guide l'utilisent. Sur chaque machine, fixez le nom et vérifiez la connectivité.

# Sur srv-glpi
sudo hostnamectl set-hostname srv-glpi
sudo apt update && sudo apt upgrade -y
ip -br a                       # notez l'IP LAN et le nom de l'interface (ex. enp0s3)

# Sur pc-client
sudo hostnamectl set-hostname pc-client
ping -c 3 192.168.1.10
Avant de continuerFaites un instantané (snapshot) des deux VM maintenant, puis un autre à la fin de chaque étape. Le pare-feu et l'IPS peuvent vous couper l'accès, un retour arrière coûte trente secondes au lieu d'une réinstallation.
Preuve pour le rapport
  • Capture de la configuration réseau des deux VM dans l'hyperviseur.
  • Sortie de ip -br a sur chaque machine et du ping client vers serveur.
Étape 02

Serveur GLPI

Hautesrv-glpiApache, PHP, MariaDB, GLPI en HTTPS.

Pile LAMP et base de données

sudo apt install -y apache2 mariadb-server php libapache2-mod-php \
  php-mysql php-curl php-gd php-intl php-ldap php-xml php-mbstring \
  php-zip php-bz2 php-bcmath php-apcu php-imap php-cli

sudo mysql_secure_installation      # mot de passe root, supprimer anonymes et base test

sudo mysql -e "CREATE DATABASE glpi CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'glpi'@'localhost' IDENTIFIED BY 'ChangezMoi-Glpi-2026!';
GRANT ALL PRIVILEGES ON glpi.* TO 'glpi'@'localhost';
GRANT SELECT ON mysql.time_zone_name TO 'glpi'@'localhost';
FLUSH PRIVILEGES;"

# Fuseaux horaires (GLPI le réclame à l'installation)
sudo mysql_tzinfo_to_sql /usr/share/zoneinfo | sudo mysql mysql

Téléchargement de GLPI

Prenez la dernière version stable. Le cahier de recettes mentionne « à partir de la version 10 » pour l'inventaire natif : la version 11 convient donc, et elle apporte la double authentification intégrée dont vous aurez besoin à l'étape 05.

VER=$(curl -s https://api.github.com/repos/glpi-project/glpi/releases/latest | grep -Po '"tag_name": "\K[^"]+')
echo "Version : $VER"
wget "https://github.com/glpi-project/glpi/releases/download/$VER/glpi-$VER.tgz"
sudo tar -xzf "glpi-$VER.tgz" -C /var/www/
sudo chown -R www-data:www-data /var/www/glpi

Certificat et hôte virtuel HTTPS

Un certificat auto-signé suffit pour la recette. Le point important est que la racine web soit le dossier public de GLPI, ce qui empêche l'accès direct aux fichiers de configuration.

sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/glpi.key -out /etc/ssl/certs/glpi.crt \
  -subj "/CN=glpi.local"

sudo tee /etc/apache2/sites-available/glpi.conf > /dev/null <<'EOF'
<VirtualHost *:80>
    ServerName glpi.local
    Redirect permanent / https://glpi.local/
</VirtualHost>

<VirtualHost *:443>
    ServerName glpi.local
    DocumentRoot /var/www/glpi/public

    SSLEngine on
    SSLCertificateFile    /etc/ssl/certs/glpi.crt
    SSLCertificateKeyFile /etc/ssl/private/glpi.key

    <Directory /var/www/glpi/public>
        Require all granted
        RewriteEngine On
        RewriteCond %{HTTP:Authorization} ^(.+)$
        RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]
        RewriteCond %{REQUEST_FILENAME} !-f
        RewriteRule ^(.*)$ index.php [QSA,L]
    </Directory>

    ErrorLog  ${APACHE_LOG_DIR}/glpi_error.log
    CustomLog ${APACHE_LOG_DIR}/glpi_access.log combined
</VirtualHost>
EOF

sudo a2enmod rewrite ssl headers
sudo a2ensite glpi && sudo a2dissite 000-default
# Cookies de session protégés (exigence du cahier des charges)
sudo sed -i 's/^session.cookie_httponly.*/session.cookie_httponly = On/' /etc/php/*/apache2/php.ini
sudo sed -i 's/^;\?session.cookie_secure.*/session.cookie_secure = On/' /etc/php/*/apache2/php.ini
sudo systemctl restart apache2

Installation de la base

Depuis le poste client, ajoutez 192.168.1.10 glpi.local dans /etc/hosts puis ouvrez https://glpi.local (vous remplacerez cette entrée par l'IP VPN à l'étape 03). Suivez l'assistant, ou faites-le en ligne de commande, ce qui est plus rapide et reproductible :

cd /var/www/glpi
sudo -u www-data php bin/console db:install \
  --db-host=localhost --db-name=glpi --db-user=glpi \
  --db-password='ChangezMoi-Glpi-2026!' --default-language=fr_FR --no-interaction

# Fermer l'installeur et protéger la conf
sudo rm -f /var/www/glpi/install/install.php
sudo chmod 640 /var/www/glpi/config/config_db.php

Connectez-vous avec glpi / glpi, puis changez immédiatement les mots de passe des quatre comptes par défaut (glpi, tech, normal, post-only) dans Administration → Utilisateurs. GLPI affiche un bandeau tant que ce n'est pas fait, et c'est une capture attendue.

Preuve pour le rapport
  • Page de connexion GLPI en https:// avec le cadenas (ou l'avertissement de certificat auto-signé).
  • Tableau de bord après connexion, sans bandeau d'alerte sur les comptes par défaut ni sur le dossier install.
  • Configuration → Générale → Système : version de GLPI et de PHP.
Étape 03

VPN WireGuard

Hautesrv-glpi + pc-clientTunnel chiffré, clé pré-partagée en plus des clés publiques.

WireGuard est le choix le plus simple à sécuriser : chiffrement moderne imposé, une seule paire de clés par machine, quelques lignes de configuration. Le cahier de recettes insiste sur la sécurisation du tunnel. Trois mesures y répondent : une clé pré-partagée qui s'ajoute à l'échange de clés, des AllowedIPs limités à la seule adresse de chaque pair, et des fichiers de clés en lecture seule pour root.

Sur le serveur

sudo apt install -y wireguard
sudo umask 077
wg genkey | sudo tee /etc/wireguard/server.key | wg pubkey | sudo tee /etc/wireguard/server.pub
wg genpsk | sudo tee /etc/wireguard/client.psk
sudo cat /etc/wireguard/server.pub     # à reporter côté client

Sur le client

sudo apt install -y wireguard
sudo umask 077
wg genkey | sudo tee /etc/wireguard/client.key | wg pubkey | sudo tee /etc/wireguard/client.pub
sudo cat /etc/wireguard/client.pub     # à reporter côté serveur

Configuration du serveur

sudo tee /etc/wireguard/wg0.conf > /dev/null <<EOF
[Interface]
Address    = 10.8.0.1/24
ListenPort = 51820
PrivateKey = $(sudo cat /etc/wireguard/server.key)

[Peer]
# pc-client
PublicKey    = COLLEZ_ICI_client.pub
PresharedKey = $(sudo cat /etc/wireguard/client.psk)
AllowedIPs   = 10.8.0.2/32
EOF
sudo chmod 600 /etc/wireguard/*
sudo systemctl enable --now wg-quick@wg0

Configuration du client

Copiez la valeur de client.psk depuis le serveur (affichez-la avec sudo cat, ne la faites pas transiter par mail).

sudo tee /etc/wireguard/wg0.conf > /dev/null <<EOF
[Interface]
Address    = 10.8.0.2/24
PrivateKey = $(sudo cat /etc/wireguard/client.key)

[Peer]
# srv-glpi
PublicKey           = COLLEZ_ICI_server.pub
PresharedKey        = COLLEZ_ICI_client.psk
Endpoint            = 192.168.1.10:51820
AllowedIPs          = 10.8.0.0/24
PersistentKeepalive = 25
EOF
sudo chmod 600 /etc/wireguard/*
sudo systemctl enable --now wg-quick@wg0

ping -c 3 10.8.0.1
# Faire pointer glpi.local vers l'adresse VPN désormais
sudo sed -i 's/^192.168.1.10 glpi.local/10.8.0.1 glpi.local/' /etc/hosts

Sur les deux machines, sudo wg show doit afficher un latest handshake récent et des compteurs de transfert qui augmentent. Sans handshake, vérifiez dans l'ordre : clés publiques inversées, clé pré-partagée différente, port 51820 bloqué par l'hyperviseur.

Preuve pour le rapport
  • sudo wg show sur le serveur et le client, avec le handshake.
  • Page GLPI ouverte depuis le client à l'adresse https://10.8.0.1 ou https://glpi.local.
  • Extrait de wg0.conf montrant la ligne PresharedKey (valeur masquée).
Étape 04

Pare-feu : seul le tunnel entre

Hautesrv-glpiUFW, tout refusé en entrée sauf UDP 51820, les services écoutent sur wg0.
Risque de se couper l'accèsFaites cette étape depuis la console de la VM dans l'hyperviseur, pas depuis une session SSH sur le LAN : cette session sera coupée dès l'activation. Vérifiez d'abord que le VPN de l'étape 03 fonctionne, c'est votre seule porte ensuite.
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing

# La seule entrée autorisée depuis le réseau : le tunnel WireGuard
sudo ufw allow 51820/udp comment 'WireGuard'

# À travers le tunnel uniquement : GLPI (HTTPS) et l'administration SSH
sudo ufw allow in on wg0 to any port 443 proto tcp comment 'GLPI via VPN'
sudo ufw allow in on wg0 to any port 80  proto tcp comment 'redirection HTTPS'
sudo ufw allow in on wg0 to any port 22  proto tcp comment 'SSH via VPN'

sudo ufw enable
sudo ufw status verbose

Depuis le client, prouvez le comportement dans les deux sens : l'IP LAN du serveur ne répond plus sur les ports web et SSH, l'IP VPN répond. Installez nmap sur le client pour cela.

sudo apt install -y nmap
nmap -Pn -p 22,80,443 192.168.1.10    # attendu : filtered
nmap -Pn -p 22,80,443 10.8.0.1        # attendu : open
ssh utilisateur@10.8.0.1              # fonctionne
ssh utilisateur@192.168.1.10          # expire

Complément peu coûteux et très visible dans un rapport : fail2ban pour bannir les tentatives SSH répétées, même à l'intérieur du tunnel.

sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
Preuve pour le rapport
  • sudo ufw status verbose complet.
  • Les deux scans nmap côte à côte : filtered sur le LAN, open à travers le VPN.
Étape 05

Double authentification

Hautesrv-glpiDeux niveaux : la connexion à GLPI et l'accès SSH au serveur.

MFA sur GLPI

GLPI 11 intègre l'authentification à deux facteurs par code temporaire (TOTP). Dans Configuration → Générale, onglet Sécurité, activez la 2FA et rendez-la obligatoire au moins pour les profils Super-Admin et Admin, avec un délai de grâce court. Chaque utilisateur enrôle ensuite son téléphone depuis ses préférences : GLPI affiche un QR code à scanner avec une application comme Aegis, FreeOTP ou Google Authenticator, et fournit des codes de secours à conserver.

Déconnectez-vous puis reconnectez-vous : GLPI demande le code à six chiffres après le mot de passe. Si vous êtes contraints à la version 10, qui n'a pas de 2FA native, portez la double authentification sur le VPN ou sur SSH, comme ci-dessous, et notez ce choix dans le rapport.

MFA sur SSH

Même à travers le VPN, un accès SSH au serveur mérite un second facteur. Le module PAM google-authenticator est standard sur Ubuntu.

sudo apt install -y libpam-google-authenticator
google-authenticator -t -d -f -r 3 -R 30 -W     # pour VOTRE compte, scannez le QR code

# Exiger le code après le mot de passe (ou après la clé)
echo 'auth required pam_google_authenticator.so' | sudo tee -a /etc/pam.d/sshd
sudo sed -i 's/^KbdInteractiveAuthentication.*/KbdInteractiveAuthentication yes/' /etc/ssh/sshd_config
echo 'AuthenticationMethods password,keyboard-interactive' | sudo tee -a /etc/ssh/sshd_config
sudo systemctl restart ssh

Gardez la session courante ouverte et testez depuis une seconde session : mot de passe, puis « Verification code ». Si ça échoue, la session encore ouverte permet de corriger.

Preuve pour le rapport
  • Écran de configuration 2FA de GLPI avec l'option obligatoire cochée.
  • Invite du code TOTP lors d'une connexion GLPI.
  • Session SSH montrant la demande « Verification code: ».
Étape 06

IPS Suricata

Hautesrv-glpiDétection d'abord, blocage ensuite via NFQUEUE, avec une preuve de blocage.

Suricata s'installe depuis le dépôt officiel du projet, plus à jour que celui d'Ubuntu. Deux fichiers seulement sont à toucher : suricata.yaml pour le réseau à protéger, et /etc/default/suricata pour passer en mode blocage. Le cahier de recettes prévient que la configuration est piégeuse : le YAML est sensible à l'indentation, validez-le avec suricata -T avant chaque redémarrage.

Installation et règles

sudo add-apt-repository -y ppa:oisf/suricata-stable
sudo apt update && sudo apt install -y suricata jq

# Réseau surveillé : le LAN et le tunnel VPN
sudo sed -i 's|HOME_NET: "\[.*\]"|HOME_NET: "[192.168.1.0/24,10.8.0.0/24]"|' /etc/suricata/suricata.yaml

# Jeu de règles Emerging Threats Open
sudo suricata-update
sudo suricata -T -c /etc/suricata/suricata.yaml -v     # doit finir par "Configuration provided was successfully loaded"

Mode IPS avec NFQUEUE

En mode NFQUEUE, le noyau confie chaque paquet à Suricata qui rend un verdict avant que le pare-feu ne poursuive. Les paquets du tunnel sont vus déchiffrés sur wg0, la sonde inspecte donc le trafic GLPI réel et pas seulement l'enveloppe WireGuard.

sudo sed -i 's/^LISTENMODE=.*/LISTENMODE=nfqueue/' /etc/default/suricata
sudo sed -i 's/^NFQUEUE=.*/NFQUEUE=0/' /etc/default/suricata

# Envoi du trafic vers la file 0 avant les règles UFW (persistant)
sudo sed -i '/^-A ufw-before-input -i lo -j ACCEPT/a -A ufw-before-input -j NFQUEUE --queue-num 0 --queue-bypass\n-A ufw-before-output -j NFQUEUE --queue-num 0 --queue-bypass' /etc/ufw/before.rules

sudo systemctl enable --now suricata
sudo ufw reload
sudo tail -n 20 /var/log/suricata/suricata.log

L'option --queue-bypass laisse passer le trafic si Suricata s'arrête. C'est un choix de disponibilité, expliquez-le dans le rapport ; enlever l'option donne un comportement « fermé en cas de panne ».

Test de détection, puis de blocage

La règle ET 2100498 se déclenche sur une réponse web de test bien connue. Elle sert d'abord à prouver la détection, puis, passée en drop, à prouver le blocage.

# 1. Détection
curl -s http://testmynids.org/uid/index.html
sudo tail -n 3 /var/log/suricata/fast.log         # ligne "GPL ATTACK_RESPONSE id check returned root"

# 2. Passer cette signature en blocage
echo '2100498' | sudo tee -a /etc/suricata/drop.conf
sudo suricata-update
sudo systemctl restart suricata

# 3. Blocage : la commande ne reçoit plus la page, l'événement est journalisé en "drop"
curl -s --max-time 10 http://testmynids.org/uid/index.html ; echo "code retour : $?"
sudo jq -c 'select(.event_type=="drop" or .event_type=="alert") | {timestamp, event_type, "sig": .alert.signature, action: .alert.action}' /var/log/suricata/eve.json | tail -n 3
Preuve pour le rapport
  • Sortie de suricata -T validant la configuration.
  • Ligne de fast.log pour la détection, puis événement drop dans eve.json avec le curl qui expire.
  • sudo ufw show raw | grep NFQUEUE montrant les règles de renvoi.
Étape 07

Client Ubuntu et agent GLPI

Moyennepc-clientInventaire natif GLPI, pas de FusionInventory.

Activer l'inventaire côté serveur

Dans GLPI : Administration → Inventaire, cochez « Activer l'inventaire ». Notez l'URL affichée, de la forme https://glpi.local/front/inventory.php : c'est le point d'entrée que l'agent utilisera à travers le VPN.

Installer l'agent sur le client

L'agent est fourni sous forme d'installeur Perl multi-distribution. Comme le certificat du serveur est auto-signé, on lui donne le certificat plutôt que de désactiver la vérification.

sudo apt install -y perl curl
# Récupérer le certificat du serveur via le VPN
sudo mkdir -p /etc/glpi-agent
openssl s_client -connect 10.8.0.1:443 -servername glpi.local </dev/null 2>/dev/null \
  | openssl x509 | sudo tee /etc/glpi-agent/glpi.crt > /dev/null

AGENT=$(curl -s https://api.github.com/repos/glpi-project/glpi-agent/releases/latest | grep -Po '"tag_name": "\K[^"]+')
wget "https://github.com/glpi-project/glpi-agent/releases/download/$AGENT/glpi-agent-$AGENT-linux-installer.pl"
sudo perl "glpi-agent-$AGENT-linux-installer.pl" --install \
  --server="https://glpi.local/front/inventory.php" \
  --ca-cert-file=/etc/glpi-agent/glpi.crt \
  --tag="salle-formation" --runnow

# Forcer un inventaire et vérifier
sudo glpi-agent --force --debug 2>&1 | tail -n 15
sudo systemctl status glpi-agent

Retournez dans GLPI : Parc → Ordinateurs doit lister pc-client avec son processeur, sa mémoire, ses disques et ses logiciels. En cas d'absence, regardez Administration → Inventaire → onglet « Journal des importations » qui explique les refus.

Preuve pour le rapport
  • Écran Administration → Inventaire avec l'option activée.
  • Fiche de pc-client dans Parc → Ordinateurs, onglet Composants.
  • Sortie de glpi-agent --force montrant l'envoi accepté.
Étape 08

Contrôle à distance

Moyennepc-client + GLPIVNC sur le client, joignable uniquement par le VPN, lancé depuis la fiche GLPI.

VNC est l'option la plus simple à intégrer : libre, sans compte tiers, et GLPI sait générer un lien vnc:// à partir de l'adresse de la machine. Le serveur VNC n'écoute que sur l'adresse VPN du client, jamais sur le LAN.

Sur le client

sudo apt install -y x11vnc
x11vnc -storepasswd                       # mot de passe VNC dans ~/.vnc/passwd

# Service qui écoute seulement sur l'IP VPN
sudo tee /etc/systemd/system/x11vnc.service > /dev/null <<EOF
[Unit]
Description=Serveur VNC (x11vnc) sur le tunnel VPN
After=display-manager.service wg-quick@wg0.service

[Service]
ExecStart=/usr/bin/x11vnc -auth guess -display :0 -usepw -rfbauth $HOME/.vnc/passwd -listen 10.8.0.2 -rfbport 5900 -forever -shared
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload && sudo systemctl enable --now x11vnc

sudo ufw allow in on wg0 to any port 5900 proto tcp comment 'VNC via VPN'
sudo ufw enable

Intégration dans GLPI

Configuration → Liens externes → Ajouter. Nom « Prise en main VNC », lien vnc://[IP]:5900, et dans l'onglet « Type d'objet » cochez Ordinateurs. La balise [IP] est remplacée par l'adresse inventoriée de la machine. Sur la fiche de pc-client, l'onglet Liens propose alors le raccourci. Pour que l'adresse résolue soit celle du VPN, l'agent doit remonter l'interface wg0, ce qui est le cas par défaut ; sinon utilisez un lien fixe vnc://10.8.0.2:5900.

Depuis le poste d'administration relié au VPN (le serveur n'ayant pas d'interface graphique, ajoutez votre machine hôte comme troisième pair WireGuard si nécessaire), un client comme Remmina ou TigerVNC Viewer ouvre la session.

Preuve pour le rapport
  • Lien externe configuré dans GLPI et l'onglet Liens sur la fiche du client.
  • Fenêtre VNC ouverte sur le bureau du client, avec un terminal affichant ip a dedans.
  • ss -ltnp | grep 5900 sur le client montrant l'écoute sur 10.8.0.2 seulement.
Étape 09

Collecteur de mails

Moyennesrv-glpiBoîte IMAP locale relevée par le collecteur natif de GLPI, création automatique de tickets.

GLPI intègre déjà le « script » demandé : un collecteur qui relève une boîte IMAP et transforme chaque mail en ticket. Il reste à lui fournir une boîte. Une messagerie locale Postfix + Dovecot évite toute dépendance à un compte externe et respecte la règle « aucune donnée réelle ».

Messagerie locale

sudo DEBIAN_FRONTEND=noninteractive apt install -y postfix dovecot-imapd bsd-mailx
sudo postconf -e 'myhostname = srv-glpi.local' 'inet_interfaces = loopback-only' 'mydestination = $myhostname, localhost'
sudo systemctl restart postfix

# Compte système qui reçoit les demandes
sudo adduser --disabled-login --gecos 'Boite support' support
echo 'support:Support-Glpi-2026!' | sudo chpasswd

# Dovecot : IMAP en clair autorisé sur localhost seulement
sudo sed -i 's/^#\?disable_plaintext_auth.*/disable_plaintext_auth = no/' /etc/dovecot/conf.d/10-auth.conf
sudo sed -i 's/^#\?mail_location.*/mail_location = mbox:~\/mail:INBOX=\/var\/mail\/%u/' /etc/dovecot/conf.d/10-mail.conf
sudo systemctl restart dovecot
ss -ltn | grep 143

Collecteur dans GLPI

Configuration → Collecteurs → Ajouter :

NomSupport par mail
Serveur de messagerielocalhost, port 143, protocole IMAP, sans TLS. Chaîne générée : {localhost:143/imap/notls}INBOX
Identifiant / mot de passesupport / celui défini plus haut
ActifOui

Le bouton « Tester la connexion » doit passer au vert. Ensuite, dans Configuration → Actions automatiques, ouvrez mailgate, mettez le mode sur CLI et la fréquence à 2 minutes. Les actions CLI ont besoin du cron système :

echo '*/1 * * * * www-data /usr/bin/php /var/www/glpi/front/cron.php' | sudo tee /etc/cron.d/glpi

Test de bout en bout

GLPI rattache un mail à l'utilisateur dont l'adresse correspond à l'expéditeur. Donnez donc à l'utilisateur normal l'adresse normal@srv-glpi.local dans sa fiche, puis envoyez un mail depuis cette identité :

echo "Bonjour, mon écran reste noir au démarrage." \
  | mail -s "Panne écran salle 2" -r normal@srv-glpi.local support@localhost

sudo -u www-data php /var/www/glpi/front/cron.php mailgate     # sans attendre le cron

Assistance → Tickets affiche « Panne écran salle 2 », demandeur normal, source « Mail ». Le rapport peut mentionner l'alternative : pointer le collecteur vers une boîte IMAP externe fictive, la configuration GLPI est identique, seuls le serveur et le port TLS changent.

Preuve pour le rapport
  • Collecteur avec le test de connexion réussi.
  • Action automatique mailgate en mode CLI et sa dernière exécution.
  • Le ticket créé automatiquement, avec l'origine « Mail » visible.

Les étapes 01 à 06 sont classées très haute ou haute et forment le socle défendable : un GLPI joignable seulement par VPN, avec MFA et IPS. Les étapes 07 à 09 sont moyennes. Entre elles, faites l'agent en premier : c'est la plus rapide, et le contrôle à distance en dépend pour le lien [IP].

Squelette du rapport de recette

Reprenez le tableau du cahier de recettes comme grille : une ligne par fonctionnalité, sa priorité, l'état (fait, partiel, non fait), la preuve, et l'écart éventuel avec ce qui était prévu. Le cahier des charges demande en plus de se positionner sur chaque risque du référentiel de sécurité, ce que votre montage couvre en grande partie.

  • Contexte et périmètre. Les deux machines, le schéma réseau avec le LAN et le tunnel, les versions installées.
  • Grille de recette. Les dix fonctionnalités du cahier avec priorité, état et renvoi vers la preuve.
  • Preuves. Les captures par étape, chacune légendée par ce qu'elle démontre.
  • Couverture sécurité. Contrôle d'accès (pare-feu, VPN), authentification (MFA, mots de passe par défaut changés), chiffrement en transit (HTTPS, WireGuard), journalisation et supervision (Suricata, fail2ban, journaux GLPI), composants à jour (versions récentes de GLPI et de l'agent).
  • Écarts et choix. Certificat auto-signé, mode bypass de l'IPS, messagerie locale à la place d'une boîte externe, et pourquoi.
  • Outils d'assistance utilisés. Le cahier des charges impose de les déclarer et de savoir justifier chaque choix.
